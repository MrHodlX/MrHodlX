# When your test oracle is somebody else's code: differential fuzzing against the reference implementation

*EntropyLab fuzzes its own rendering and wallet pipelines against independent
implementations — including a C++ reference compiled at a pinned commit. The
hard part wasn't finding mismatches. It was figuring out whose rounding is
the truth.*

Unit tests with hand-picked vectors tell you the cases you already thought
of. Differential fuzzing tells you about the ones you didn't: feed the same
input to two independent implementations, require identical output, repeat a
few thousand times. EntropyLab runs this pattern in three places, and each
one taught a different lesson.

## The setup

All three fuzzers share a discipline:

- **Deterministic inputs.** A seeded xorshift64 PRNG generates the input
  stream. A CI failure reproduces locally with the logged `FUZZ_SEED` and
  `FUZZ_ITERATIONS` — no "flaky fuzzer" shrugging.
- **The app side is the shipped code.** Not a copy, not a port. The LifeHash
  fuzzer evaluates `src/js/lifehash.js` with its browser globals shimmed; the
  multisig fuzzer *slices the actual functions out of `src/js/app.js` by
  bracket-matching the source text* and imports the slice. If someone edits
  the app, the fuzzers exercise the edit. If the slicing breaks, it throws
  loudly instead of silently testing nothing.
- **The app never sees the randomness.** The PRNG only generates test inputs
  — a policy-safe use in a project whose first rule is "never invent entropy
  for key material."

## LifeHash: three implementations walk into a bar

LifeHash is the visual fingerprint icon — Sparrow Wallet shows one for every
key, and users compare them by eye to spot a swapped xpub. If EntropyLab's
icon differs from Sparrow's for the same fingerprint, a careful user sees two
different images and thinks something is wrong. Cross-wallet agreement *is*
the feature.

So the fuzzer runs every input through two full public pipelines and requires
the rendered pixels — decoded PNG RGB, including the hand-rolled PNG encoder
and module-size scaling — to be byte-identical:

```
ours:   fromFingerprint(fp, moduleSize) -> PNG data URL -> decoded RGB
theirs: LifeHash.makeFrom(...).colors   (the reference side)
```

Except "the reference" turned out to be a choose-your-own-adventure:

1. **The Blockchain Commons C++ implementation** is the spec in practice.
   `fuzz-cpp.mjs` clones it at a pinned commit, *verifies the checkout is at
   exactly that commit with no local modifications*, builds it with
   `-ffp-contract=off` (so the compiler can't fuse multiply-adds and round
   differently from the source's separate operations), and runs it as a
   long-lived child process speaking a line protocol.
2. **The npm `lifehash` package** is what most JS projects use — and it
   computes its colour arithmetic in double precision where the C++ uses
   single-precision `fmodf`/`powf`/`sqrtf`. The two disagree on roughly **1%
   of fingerprints**. Not a bug in either: an unwritten part of the spec,
   resolved differently.

EntropyLab follows the C++ semantics (Sparrow compatibility is the contract),
so `fuzz.mjs` does something unusual: it copies the pinned npm package to a
scratch dir and *surgically substitutes the two float-precision functions*
for their `Math.fround` equivalents, keeping everything else — hashing, the
Game of Life, gradient selection, symmetry — as a genuine independent
implementation. Each substitution must match the package source exactly once,
so a package update fails the patch loudly instead of drifting silently.

And before any fuzzing runs, both sides must reproduce seven vectors
generated by the C++ reference — including three the *unpatched* package gets
wrong, proving the substitution took effect. A fuzzer whose comparisons
silently no-op must fail here, loudly.

**Lesson:** "matches the reference" is meaningless until you know *which*
reference, at *which* commit, with *which* rounding. The 1% disagreement
wasn't found by reading code — it fell out of the fuzzer, and then had to be
explained before it could be engineered around.

## Multisig: fuzzing the parser's etiquette, not just the math

The multisig fuzzer (`fuzzing/msig/fuzz.mjs`) compares EntropyLab's whole
multisig output pipeline against an independent stack (`@scure/bip32` +
`@scure/btc-signer`) across script kind × standard × key order × network ×
threshold permutations. Addresses must match the scure-computed reference at
every sampled index.

But the interesting assertions aren't the arithmetic — they're the *input
etiquette*:

- **Suffix tolerance.** Users paste xpubs decorated with trailing wildcards
  (`/0/*`, `/<0;1>/*`, a lone trailing slash). The app's real
  `hodlFilterXpub`/`hodlParseKeyOrigin` must parse each decoration to the
  identical origin and key — and *every downstream output* (branch
  descriptors, the multipath watch-only descriptor, every address) must be
  byte-identical to the undecorated run. A parser that "accepts" a suffix but
  quietly changes the derivation is a fund-loss bug wearing a UX fix.
- **Honored trailing paths.** A numeric path after the key (`xpub…/0/20`) is
  descriptor key derivation and *must* change the output — and the output
  must equal the reference derived through the same path. The fuzzer pins
  both directions: decoration that must be ignored, and decoration that must
  be honored.
- **Checksum round-trips.** Every descriptor the app emits is fed back
  through the rust-miniscript WASM engine, which verifies the BIP380 checksum
  before deriving. A checksum regression fails against real output, not a
  mocked check.

**Lesson:** the dangerous parser bugs are at the boundary between "tolerant"
and "correct." Fuzz the tolerance itself, and assert on *all* the outputs the
parse feeds — a parser that parses right but derives wrong is still wrong.

## The meta-lesson

Every one of these harnesses contains more code guarding the *comparison*
than doing the comparing: pinned commits, patch-exactly-once substitutions,
non-vacuity vectors, delivery proofs, reproducible seeds. That's not
overhead — that *is* the harness. A differential fuzzer is only as good as
its answer to two questions:

1. **How do you know both sides actually ran?** (Non-vacuity vectors,
   slice-failure exceptions, patch-match counts.)
2. **When they disagree, how do you know which one is right?** (A third
   implementation, a written spec, or — as with the 1% float disagreement —
   the de-facto standard your users' other tools follow.)

Two implementations agreeing proves little; two *independent* implementations
agreeing on thousands of seeded inputs, with a third arbitrating the
disagreements, is the closest thing to a specification a underspecified
format gets.
